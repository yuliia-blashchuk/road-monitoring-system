# KAN-113. Звірка опису API (Swagger / OpenAPI) з реальними ендпоінтами

Документація API генерується автоматично з коду і доступна на `http://localhost:8000/docs`.
Ми перевірили, чи вона каже правду: які ендпоінти є, хто має до них доступ і які
помилки вони реально повертають.

## Як перевіряли

Автотест `backend/tests/test_openapi_contract.py` (запуск: `docker compose exec api pytest tests/test_openapi_contract.py -v`):

| ID | Перевірка |
|---|---|
| TC-DOC-01 | Кожен ендпоінт має опис українською, групу (tag) і успішну відповідь |
| TC-DOC-02 | Кожна помилка 4xx у документації має схему тіла відповіді |
| TC-DOC-03 | Помилки бізнес-правил (конфлікт 409, ліміт 429, не знайдено 404) описані там, де їх повертає код |
| TC-DOC-04 | Кожен ендпоінт викликано від імені аноніма й 6 ролей (водій, диспетчер, поліція, підрядник, адміністратор, Data Governance); кожен отриманий код є в документації |
| TC-DOC-05 | Ендпоінти, згадані в README, існують з тим самим методом і шляхом |

Тест запущено на `main` до виправлень: **4 перевірки з 5 не пройшли**. Після виправлень пройшли всі 5.

## Знайдені розбіжності й виправлення

| № | Розбіжність | Де | Виправлення |
|---|---|---|---|
| 1 | Відповідь **401** (немає або прострочений токен) не описана, хоча її повертають 27 з 32 ендпоінтів (перевірка на `main` до KAN-109) | усі захищені ендпоінти | 401 додано на рівні роутерів (`responses=errors(401, …)`) |
| 2 | Відповідь **403** не описана, хоча роль без доступу її отримує | `/consents/*`, `/reports/nearby`, `/reports/{id}/confirm`, `/reports/my`, `/queue`, `/audit/actions`, `/admin/*` | 403 додано |
| 3 | Помилки «Теж бачу» не описані: заявку не знайдено (404); закрита, власна або вже підтверджена (409) | `POST /reports/{id}/confirm` | 404 і 409 з поясненням |
| 4 | Повтор коду типу проблеми (409) не описаний | `POST /admin/problem-types` | 409 додано |
| 5 | 28 описаних помилок не мали схеми тіла: у `/docs` не видно, що прийде у відповіді | усі роутери | Спільні схеми `ErrorOut`, `ValidationErrorOut`, `ConsentMissingOut` (`app/core/openapi.py`), підставляються автоматично |
| 6 | 403 через відсутню згоду водія має інший формат (`detail` - об'єкт зі списком згод), який не був описаний | `POST /reports` | Описано обидва варіанти 403 |
| 7 | Ендпоінти перевірки стану без опису українською («Health», «Health Db») | `/health`, `/health/db` | Додано описи |

Поведінка API не змінювалась: виправлено лише документацію. Усі тести бекенду проходять.

## Формати помилок

| Код | Формат тіла | Приклад |
|---|---|---|
| 401, 403, 404, 409, 429 | `{"detail": "текст"}` | `{"detail": "Недостатньо прав для цієї дії"}` |
| 422 | `{"detail": [{"loc": [...], "msg": "текст"}]}` | `{"detail": [{"loc": ["body", "location"], "msg": "Ділянка не обслуговується"}]}` |
| 403 (бракує згоди) | `{"detail": {"message": "текст", "missing_consents": [...]}}` | `{"detail": {"message": "…", "missing_consents": ["contact"]}}` |

Фронтенд показує користувачу текст із `detail` (для 422 - біля поля з `loc`), див. KAN-115.

## Для README і звіту

Усі шляхи, згадані в README, існують (TC-DOC-05). Але 13 ендпоінтів у README не описані:
згоди (`/consents/*`, 4 шт.), `GET /auth/me/permissions`, «Теж бачу» (`/reports/nearby`,
`/reports/{id}/confirm`), підрядні роботи (`/work-orders`, 3 шт.), `POST /admin/problem-types`,
`GET /admin/access-policies`, `GET /admin/contractors`. Пропонуємо додати посилання на цей перелік у README в межах KAN-112.
Таблицю вище можна використати у звіті (розділ «Опис прототипу», бекенд).
