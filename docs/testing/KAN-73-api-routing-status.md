# KAN-73. Тест-кейси API: маршрутизація і статуси

Перевіряємо дві речі через HTTP, так само як їх використовує фронтенд:

1. **Маршрутизація** (KAN-58, F-10, F-23): кожен тип проблеми в кожному районі потрапляє
   до служби за таблицею маршрутизації, з правильною копією й початковим пріоритетом.
2. **Статуси** (KAN-59, п. 2.2, БП-3, БП-6): допустимі переходи працюють, а недопустимі
   відхиляються й нічого не змінюють.

Очікувані результати записані в тесті окремо від коду (таблиці нижче). Тому тест
помітить, якщо правила в коді зміняться без зміни вимог.

Автотести: `backend/tests/test_api_routing_status.py`
(запуск: `docker compose exec api pytest tests/test_api_routing_status.py -v`).
Результат: **58 пройдено, 1 очікувана помилка (дефект D1)**.

## Таблиця переходів статусів (очікування)

| З якого | На який | Хто може |
|---|---|---|
| Нова | Прийнята, Відхилена (з причиною) | служба (диспетчер, поліція) |
| Прийнята | В роботі | служба або призначений підрядник |
| Прийнята | Відхилена (з причиною) | служба |
| В роботі | Усунена | служба (якщо підрядника немає) |

| Виконана | Усунена | лише служба |

| D1 | Заявка рівно на межі двох районів не потрапляє до жодної служби | `POST /reports`, `problem_type=pothole`, `latitude=49.84`, `longitude=24.03` | служба одного з районів | 201, `service = null` — заявку отримує лише адміністратор | Середня | `routing/repository.py` перевіряє зону через `ST_Contains`, який не враховує точки на межі. лишається зеленим, а щойно його виправлять, тест про це повідомить, і позначку треба
прибрати.

та строк у минулому (`test_reports_status`), права інших ролей (KAN-74, `test_rbac_negative`).
