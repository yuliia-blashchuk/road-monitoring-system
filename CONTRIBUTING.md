# Правила роботи з репозиторієм

## Гілки

- `main` — завжди робоча, перевірена версія. **Напряму в `main` ніхто не пушить**, тільки через Pull Request.
- Для кожної задачі створюється окрема гілка від свіжого `main`.

Назва гілки: `тип/ключ-задачі-короткий-опис`, латиницею, малими літерами, через дефіс.

| Тип | Коли | Приклад |
|---|---|---|
| `feature/` | нова функція | `feature/RM-12-create-report` |
| `fix/` | виправлення помилки | `fix/RM-30-wrong-priority` |
| `docs/` | документація | `docs/RM-5-use-cases` |
| `chore/` | налаштування, залежності, інфраструктура | `chore/RM-3-backend-skeleton` |
| `test/` | лише тести | `test/RM-41-report-api` |

`RM-12` — ключ задачі з Jira, щоб по гілці було видно, до якої задачі вона належить.

## Коміти

Формат: `тип: що зроблено` (коротко, в теперішньому часі).

```
feat: add endpoint for creating report
fix: reject report outside city boundary
docs: describe UC-02
chore: add PostGIS to docker compose
test: cover status transitions
refactor: move priority calculation to service
```

Один коміт — одна логічна зміна. Не комітимо `.env`, паролі та особисті налаштування.

## Порядок роботи над задачею

1. Оновити `main`: у VS Code перемкнутися на `main` → **Sync Changes** (або `git switch main` → `git pull`).
2. Створити гілку: `git switch -c feature/RM-12-create-report`.
3. Робити зміни й коміти.
4. Перед пушем перевірити: `docker compose exec api ruff check .` і `docker compose exec api pytest`.
5. Запушити гілку (**Publish Branch** у VS Code) і на GitHub відкрити **Pull Request** у `main`.
6. Заповнити шаблон PR і призначити рев'юера.
7. Після схвалення: **Squash and merge**, потім **Delete branch**.

## Code review

- Кожен PR має отримати **щонайменше 1 схвалення (Approve)** від іншого учасника. Автор сам свій PR не схвалює.
- Автоматичні перевірки (GitHub Actions: Ruff + pytest) мають бути зелені.
- Рев'юер дивиться на:
  - чи зроблено те, що в задачі, і нічого зайвого;
  - чи код у правильному модулі й шарі (router → service → repository);
  - чи перевіряються права доступу на сервері;
  - чи не потрапили в код паролі, ключі, персональні дані;
  - чи є тест на нову логіку;
  - чи зрозумілі назви та чи немає закоментованого «мертвого» коду.
- Зауваження пишемо конкретно й ввічливо: що не так і як краще. Автор відповідає на кожен коментар (виправив / пояснив чому ні).
- Рев'ю робимо протягом 1 робочого дня, щоб ніхто не чекав.
